02. como_trabajo
Prioridad

La cobertura no es pareja: priorizo por riesgo, impacto en el usuario final y criticidad del flujo de negocio. Los escenarios de menor riesgo quedan en testing exploratorio o fuera del alcance inicial.

Reporte

Un defecto bien documentado incluye pasos de reproducción precisos, resultado esperado versus obtenido, evidencia y entorno. Esa disciplina reduce el tiempo de reproducción y evita idas y vueltas innecesarias con desarrollo.

Automatización

Automatizo los flujos estables y de mayor valor — regresión y casos críticos de negocio. La UI que cambia con frecuencia o requiere criterio humano se mantiene bajo testing exploratorio manual.

IA

Incorporo herramientas de IA para acelerar el diseño de casos, la evidencia y la documentación (ver sobre_mí). La decisión de qué probar y por qué sigue siendo un criterio profesional, no delegable.

Proceso

No solo ejecuto el proceso de QA que me dan: en los proyectos que llevo soy el punto de referencia entre QA, desarrollo y producto para definir cuándo algo está "listo para release". Armé el estándar de reporte de bugs y la documentación de test plan/suites que usa el equipo, para que sumarse a un proyecto no dependa de preguntarme a mí.

Test strategy

Approach al arrancar un producto nuevo

Risk-based Test planning
Primera semana
Mapeo los flujos críticos de negocio junto a producto — no arranco escribiendo casos hasta entender qué es lo más caro si falla.
Priorización
Clasifico por riesgo (impacto × probabilidad), no por orden de desarrollo: lo crítico se prueba primero aunque el feature esté "casi listo" y otra cosa esté completa.
Cobertura
Defino qué queda en regresión, qué en exploratorio manual, y qué directamente no se prueba porque el riesgo no lo justifica — la cobertura no es pareja a propósito.
"Listo para release"
Acuerdo con dev y product owner qué debe cumplirse (cobertura mínima, bugs abiertos por severidad) antes de dar luz verde — no es una decisión unilateral de QA.
Auditoría de accesibilidad

WCAG 2.1 — hallazgo y remediación

WCAG 2.1 AA Auditoría manual
Criterio
1.4.11 Non-text Contrast (AA)
Hallazgo
El estado de foco de los inputs del checkout tiene un contraste de ~1.8:1 contra el fondo — prácticamente invisible para navegación por teclado y usuarios con baja visión.
Impacto
Quien navega por teclado o usa un lector de pantalla con zoom no puede identificar en qué campo está parado; bloquea el flujo de pago, no es un defecto cosmético.
Remediación
Outline sólido de 2px con contraste ≥3:1 más un segundo indicador (fondo), para no depender únicamente del color.
Root cause analysis

Bug intermitente en checkout

RCA SQL Logs
Síntoma
El estado "Activa" de la suscripción tardaba hasta 8s en reflejarse en la UI tras el pago, y a veces no aparecía sin refrescar la página.
Investigación
Los logs mostraban que el webhook de confirmación de pago llegaba antes de que la transacción SQL del alta terminara de commitear — una condición de carrera entre el evento asíncrono y la escritura en base de datos.
Causa raíz
El endpoint devolvía 201 antes de confirmar el commit; el polling del frontend a veces leía el registro justo antes de que existiera.
Verificación
Reproducido forzando el timing en un entorno local; fix validado moviendo la respuesta después del commit y agregando retry con backoff en el polling.
Reporte de bug

Ticket listo para desarrollo, sin idas y vueltas

Jira Bug report
Resumen
El botón "Confirmar pago" queda deshabilitado si se edita la cantidad en el carrito durante el checkout.
Pasos para reproducir
  1. Agregar un producto al carrito y llegar a checkout.
  2. Editar la cantidad desde el input numérico del ítem.
  3. Sin recargar la página, hacer clic en "Confirmar pago".
Esperado vs. obtenido
Esperado: el total se recalcula y el botón permite confirmar. Obtenido: el botón queda deshabilitado indefinidamente; solo se habilita recargando la página.
Entorno · Severidad
Chrome 126, Staging, cuenta de prueba con plan mensual · Alta — bloquea la compra ante cualquier edición de cantidad.
Automatización

Fixture de datos vía API + Page Object

Playwright TypeScript Fixtures 
// fixtures.ts — el estado se crea por API, no clickeando la UI
export const test = base.extend<{ activeSubscription: Subscription }>({
  activeSubscription: async ({ request }, use) => {
    const res = await request.post('/api/subscriptions', { data: { plan: 'annual' } });
    const sub = await res.json();
    await use(sub);
    await request.delete(`/api/subscriptions/${sub.id}`); // teardown
  },
});

// checkout.spec.ts
test('el estado de la suscripción se refleja en el dashboard', async ({ page, activeSubscription }) => {
  await page.goto(`/dashboard/${activeSubscription.id}`);
  await expect(page.getByTestId('subscription-status')).toHaveText('Activa');
});
Integridad de datos

Detección de registros huérfanos

SQL Data integrity 
-- Suscripciones activas en pagos sin reflejo en el caché mobile
SELECT p.subscription_id, p.user_id, p.updated_at
FROM payments.subscriptions p
LEFT JOIN mobile.subscription_cache m
  ON m.subscription_id = p.subscription_id
WHERE p.status = 'active'
  AND (m.subscription_id IS NULL
       OR m.synced_at < p.updated_at - INTERVAL '15 minutes');

Corre en cada regresión de plataformas con web + mobile para detectar desincronización antes de que la reporte el usuario.
