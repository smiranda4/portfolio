02. how_i_work
Priority

I optimize for risk, not for volume. The critical path gets the strongest evidence; lower-risk areas stay lightweight or exploratory.

Reporting

A strong bug report answers three things immediately: what broke, what was expected, and how to reproduce it. That keeps triage short and reduces churn with development.

Automation

I automate the stable, high-value checks: critical journeys, API contracts, and regression loops. Anything unstable or judgment-heavy stays manual.

AI

I use AI as a force multiplier for test design, evidence gathering, and documentation, but product context and quality judgment stay with the QA engineer.

Process

I act as the QA/Dev/PO technical reference, own release-readiness criteria, and document the standards the team follows so quality is consistent, not heroic.

Testing AI products

Risk matrix for an AI assistant

AI Multi-tenant Risk-based
Uploaded document with injected instructions
The assistant ignores them, answers from the source only, and the citation points at the real passage. Tested with instructions hidden in headers, footers, and white-on-white text.
Question about another organization’s documents
403 at the API and nothing leaks into the chat answer — checked per role, not only as admin, and also through the chat channels, not only the web UI.
Citation to a page that doesn’t exist
A defect even when the answer reads well. Every citation is verified against the indexed document, not against how convincing the text sounds.
Same question, five runs
Wording may vary; facts and citations may not. Drift in facts between runs blocks the release.
Release criteria
Agreed with product and engineering: all four scenarios pass deterministically, plus explicit, written risk acceptance for anything intentionally left untested.
evidence/wcag-1.4.11-finding.md
Accessibility audit

WCAG 2.2 — finding and remediation

WCAG 2.2 AA Manual audit
Criterion
1.4.11 Non-text Contrast (AA)
Finding
The focus state of checkout inputs has a contrast ratio of ~1.8:1 against the background — nearly invisible for keyboard users and low-vision users.
Impact
Users navigating by keyboard or using a screen reader with zoom cannot tell which field is active; this blocks the payment flow and is not a cosmetic issue.
Remediation
Use a solid 2px outline with contrast ≥3:1 plus a secondary visual indicator on the field background instead of relying only on color.
evidence/rca-checkout-race-condition.md
Root cause analysis

Intermittent checkout bug

RCA SQL Logs
Symptom
The subscription took up to 8s to show as “Active” in the UI after payment, and sometimes did not appear until the page was refreshed.
Investigation
Logs showed the payment webhook arrived before the SQL subscription insert finished committing — a race condition between the asynchronous event and the database write.
Root cause
The endpoint returned 201 before the commit was confirmed; the frontend poller sometimes read the record just before it existed.
Verification
Reproduced by forcing timing in a local environment; fix validated by moving the response after the commit and adding retry with backoff in the polling flow.
evidence/QA-1427-confirm-payment-disabled.md
Bug report

Ticket ready for development, without back-and-forth

Jira Bug report
Summary
The “Confirm payment” button remains disabled if the quantity in the cart is edited during checkout.
Steps to reproduce
  1. Add a product to the cart and proceed to checkout.
  2. Edit the quantity from the item input.
  3. Without reloading the page, click “Confirm payment”.
Expected vs. actual
Expected: the total recalculates and the button allows confirmation. Actual: the button remains disabled indefinitely and only re-enables after a page refresh.
Environment · Severity
Chrome 142, Staging, test account with monthly plan · High — blocks checkout whenever quantity is edited.

export const test = base.extend<{ activeSubscription: Subscription }>({
  activeSubscription: async ({ request }, use) => {

  constructor(private page: Page) {}

  status() { return this.page.getByTestId('subscription-status'); }
}

evidence/orphaned-subscriptions.sql
Data integrity

Detection of orphaned records

SQL Data integrity 
-- Active subscriptions that are missing a mobile cache reflection
SELECT p.subscription_id, p.user_id, p.updated_at
FROM payments.subscriptions p
LEFT JOIN mobile.subscription_cache m
  ON m.subscription_id = p.subscription_id
WHERE p.status = 'active'
  AND (m.subscription_id IS NULL
       OR m.synced_at < p.updated_at - INTERVAL '15 minutes');

Runs during regression across web and mobile platforms to catch desynchronization before users report it.
